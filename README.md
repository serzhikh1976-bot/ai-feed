# AI Feed Generator — MVP (этап 3 завершён: категории + сборка XML)

Что уже реализовано и протестировано:
- Парсинг Excel/CSV с корректной обработкой кириллицы (UTF-8).
- «Умный» маппинг колонок по ключевым словам в заголовках, с fallback на порядок колонок.
- Валидация: пустой файл, неподдерживаемый формат, отсутствие обязательных колонок.
- Определение невалидных ссылок на картинку → статус warning, подставляется заглушка.
- Асинхронная (фоновая) обработка с polling — без блокирующего HTTP-запроса.
- Простой веб-интерфейс: drag-and-drop, прогресс-бар, лог по каждому товару, **кнопка скачивания активна**.
- Генерация name/description/params через ИИ на украинском языке, с retry-логикой.
- Матчинг категории Prom.ua — двумя AI-вызовами (top-level ветка бесплатно в первом вызове, точная категория — вторым узким вызовом).
- **Сборка и скачивание готового XML-фида** (YML-формат, совместимый с Prom.ua/Rozetka) — `GET /api/jobs/:id/download`.

Следующий этап — email-идентификация и лимиты.

## Скачивание фида

После завершения обработки (`status: completed`) кнопка «Скачать XML-фид» в интерфейсе становится активной — если хотя бы один товар получил статус success или warning. В фид попадают только они; товары со статусом error исключаются полностью (ни одного битого `<offer>`).

Прямой endpoint: `GET /api/jobs/:requestId/download` — отдаёт `feed.xml` с заголовком `Content-Disposition: attachment`.

Граничные случаи, которые обработаны:
- Job ещё не завершён → 409 с понятной ошибкой.
- Job не найден → 404.
- Все товары ушли в error (нечего скачивать) → 422 с понятной ошибкой.

## Матчинг категорий: как это работает

1. Справочник (`data/prom_categories.xls`, ваш файл на 5822 категории) грузится один раз при старте сервера.
2. Первый AI-вызов (этап 2) получает список из 58 top-level веток и возвращает `categoryTopLevel` вместе с name/description/params — бесплатно, в том же запросе.
3. Локально (без AI) сужаем справочник до этой ветки и отбираем 10-15 кандидатов по ключевым словам (word-boundary поиск, с поправкой на пару известных синонимов вроде павербанк/повербанк).
4. Второй, узкий AI-вызов выбирает точный `categoryId` из этого короткого списка — не может придумать несуществующий id (это строго провалидировано в коде).

**Честно про точность:** локальный keyword-поиск на реальных тестовых товарах нашёл точную категорию в кандидатах не во всех случаях (сказывается разница между языком поставщика и каталога, разные словоформы, официальные названия vs разговорные). После перехода с фиксированной длины префикса на отсечение окончаний (стемминг) точность заметно выросла: на 5 контрольных товарах (футболка, кросівки, куртка, павербанк, адаптер) нужная категория теперь попадает в кандидаты во всех 5 случаях, обычно на 1-2 позиции. Финальное решение всё равно за ИИ (второй вызов), который смотрит на уже чистый украинский текст и делает осмысленный выбор — локальный поиск отвечает только за то, чтобы предложить ему правильный набор вариантов.

**Реальный найденный и исправленный баг:** на живом прогоне (3 товара) куртка попала не в ту категорию ("Жіноча білизна і купальники" вместо "Жіночі куртки") — потому что "куртка"/"куртки" это разные словоформы одного слова ровно одинаковой длины (6 букв), и старая эвристика по префиксу их не связывала. ИИ на втором шаге не виноват — нужной категории физически не было в списке, который ему передали. Починено стеммингом (отсечение типичных украинских окончаний перед сравнением).

**Все fallback-и, если что-то пошло не так:**
- Справочника вообще нет на диске → все товары получают `DEFAULT_CATEGORY_ID` (по умолчанию `1`), это явно логируется при старте сервера.
- ИИ вернул несуществующую top-level ветку → откат на поиск по всему справочнику (5822 категории вместо узкой ветки — медленнее, но не проваливает товар).
- Второй AI-вызов не смог выбрать после ретраев → берётся лучший локальный кандидат автоматически, статус товара помечается `warning` с пояснением "стоит проверить".

Ни один из этих случаев не переводит товар в `error` — категория это одно поле фида, а не весь результат; при осечке лучше приблизительная категория с пометкой на проверку, чем потерянный товар.

## Настройка справочника категорий

Положите ваш xls-файл в `data/prom_categories.xls`, либо укажите свой путь в `.env`:
```
CATEGORY_DIRECTORY_FILE=./data/ваш_файл.xls
DEFAULT_CATEGORY_ID=1
```

**Если разворачиваете поверх своего репозитория ai-feed:** у вас файл уже лежит в корне как `Prom.ua_categories_15_08_2026.xls` — либо переместите его в `data/prom_categories.xls` (тогда `.env` можно не трогать), либо просто укажите в `.env`:
```
CATEGORY_DIRECTORY_FILE=./Prom.ua_categories_15_08_2026.xls
```

## Настройка ИИ

1. Скопируйте `.env.example` в `.env`:
   ```bash
   cp .env.example .env
   ```
2. Откройте `.env` и укажите:
   - `AI_PROVIDER=openai` или `AI_PROVIDER=gemini`
   - Соответствующий ключ: `OPENAI_API_KEY=...` или `GOOGLE_AI_API_KEY=...`
   - `AI_MODEL` можно оставить пустым — тогда используется дефолт из ТЗ (gpt-4o-mini / gemini-2.5-flash).
   - `DEFAULT_BRAND` — если хотите жёстко задать бренд для всех товаров в прогоне (сценарий А из ТЗ). Оставьте пустым, чтобы ИИ искал бренд сам.
   - `CATEGORY_DIRECTORY_FILE` / `DEFAULT_CATEGORY_ID` — см. раздел про категории выше.

**`.env` никогда не должен попадать в архивы/git — там секретные ключи.** Файл уже добавлен в `.gitignore`.

## Тестирование без реальных AI-затрат

Есть встроенный `AI_PROVIDER=mock` — заглушка, которая имитирует ответ ИИ (включая случайные сбои для честной проверки retry-логики) без единого реального запроса к OpenAI/Gemini. Полезно, чтобы проверить весь пайплайн (upload → parsing → AI → статусы) бесплатно, прежде чем тратить реальные токены.

```bash
# в .env: AI_PROVIDER=mock
npm start
```

**Важно:** `mock` — только для разработки. Никогда не используйте его в проде — клиенты получат сгенерированные заглушки вместо реального контента.

## Быстрый старт

Откройте **http://localhost:3000** в браузере — там простой интерфейс: drag-and-drop зона для файла, прогресс-бар (обновляется через polling каждые 2 сек, без блокирующего запроса), сводка по success/warning/error и лог по каждому товару. Кнопка «Скачать XML» пока задизейблена — сборка XML появится на этапе 3.

## Тест полного цикла через HTTP (как будет работать фронтенд)

```bash
# 1. Загрузка файла
curl -F "file=@/путь/к/вашему/файлу.csv" http://localhost:3000/api/upload
# → {"requestId":"...", "totalItems":3, ...}

# 2. Опрос статуса (повторять каждые 2-3 сек, как будет делать фронтенд)
curl http://localhost:3000/api/jobs/ВАШ_REQUEST_ID
```

В ответе job'а — общий статус, счётчик processedItems/totalItems, и массив items с полями каждого товара + его статусом (success/warning/error) и сообщением.

## Что стоит попробовать сломать при тестировании

- Файл с колонками в неожиданном порядке или с непривычными названиями заголовков.
- Файл с пустыми ячейками цены или артикула — должен уйти в error, а не уронить весь job.
- Файл больше 20 строк — должен обрезаться до 20 (поле `truncated: true` в ответе upload).
- Не-Excel/CSV файл (например .txt) — должен вернуть 400 с понятной ошибкой.
- Файл с BOM или в другой кодировке — стоит проверить, не относится ли к вашим реальным поставщикам.

## Правила Prom.ua, учтённые в этой версии

По официальной документации Prom.ua ("Export Products Sheet") в код внесены исправления, применимые и к YML/XML-фиду (не только к нативному Excel-импорту):

- **Лимит описания поднят с 500 до 2000 символов** (официальный лимит поля — 12160; 500 было искусственным ограничением из черновика ТЗ). Промпт по-прежнему просит писать лаконично.
- **Лимит артикула — 25 символов.** Товары с более длинным артикулом уходят в `error` с понятным сообщением (не обрезаются молча — обрезка сломала бы сопоставление с системой поставщика).
- **`available` теперь честный, а не всегда `true`.** Если в файле поставщика есть колонка наличия/количества (распознаётся по ключевым словам: наявність, кількість, залишок, остаток, stock) — используется она. Если колонки нет — товар помечается `available="false"` (это официальный дефолт Prom.ua при отсутствии данных о наличии, а не наша прихоть).
- **Бренд — отдельный `<vendor>` тег**, а не один из `<param>`. Учтите: по правилам Prom.ua бренд импортируется, только если он уже есть в базе производителей площадки — это невозможно проверить программно с нашей стороны, при сомнениях используйте реальный проверенный бренд или "No Name".

**Что НЕ применялось (специфично для другого формата импорта):** тот же официальный документ описывает нативный Excel-шаблон Prom.ua ("Export Products Sheet") — это отдельный от YML способ импорта с другими полями (раздельные RU/UA колонки, категория через URL вместо числового id). Мы сознательно остаёмся на YML/XML, поэтому эти правила не переносились в код. Если решите добавить экспорт в нативный Excel-формат — это отдельный экспортер, а не патч текущего XML.

## Структура YML — сверено с официальной документацией Prom.ua

Получен официальный документ "Імпорт через YML — формат файлу" — до этого структура XML опиралась на неформальный пример из черновика ТЗ. Внесены уточнения:

- **`<!DOCTYPE yml_catalog SYSTEM "shops.dtd">`** — добавлена техническая строка сразу после XML-декларации, как того требует официальный формат.
- **`<name_ua>` / `<description_ua>`** — добавлены отдельные украинские теги (дублируют `<name>`/`<description>`, т.к. мы и так генерируем контент только на украинском). Важное правило из документа: если заполнено только одно из пары — перевод не обновится, поэтому заполняем оба тега одинаковым значением.
- **`<vendorCode>`** — добавлен отдельный тег для артикула (официально корректный тег для этого поля; раньше у нас было только `offer id`, что технически не то же самое поле).
- **`<portal_category_id>`** — добавлен явный тег для сопоставления с реальной категорией маркетплейса, дублирует значение `<categoryId>` для надёжности (документ описывает `<categoryId>` как ссылку на **собственный** блок `<categories>` в файле, а `<portal_category_id>` — как прямое указание категории на самом Prom.ua; мы используем реальные id из справочника Prom.ua в обоих местах, так что расхождений это не создаёт, но `portal_category_id` — более прямой и однозначный сигнал).
- **`selling_type="r"`** — явно помечены товары как розничные (по умолчанию), значение из документа (`r`/`w`/`u`/`s`).

## Известные ограничения текущего этапа

- Job'ы хранятся в памяти процесса — перезапуск сервера = все задачи теряются (по плану это ожидаемо для MVP, см. ТЗ).
- Email-верификация и лимиты — не реализованы, следующий этап.
- Матчинг категорий делает 2 AI-вызова на товар вместо 1 (name/description + отдельный category) — это осознанный компромисс точность/стоимость, обсуждённый отдельно. Увеличивает потолок запросов на прогон (см. ТЗ 5.1 про 60 запросов — с категориями потолок выше, стоит пересчитать).
- Retry-логика и категорийный матчинг проверены на mock-провайдере (плюс структура запросов сверена с документацией OpenAI/Gemini на август 2026) — живой сквозной тест на реальном ключе именно для категорийного шага ещё не проводился в этом окружении (нет доступа к api.openai.com/googleapis.com из песочницы). Стоит проверить у себя первым делом, особенно точность выбора категории.

## Безопасность зависимостей (важно при `npm install`)

При установке `npm audit` может показывать уязвимости — вот что с ними сделано:

- **fastify** — обновлено до v5 (было v4), закрывает 3 CVE (DoS, обход валидации Content-Type, спуфинг протокола через заголовки). Проверено: весь функционал (upload, job-статус, polling) работает без изменений после апгрейда.
- **xlsx (SheetJS)** — это единственная оставшаяся уязвимость, и она реальная, не шум: пакет `xlsx` в обычном npm-реестре (версия 0.18.5) содержит непропатченную prototype pollution и ReDoS в парсере, а сам SheetJS **сознательно не публикует фикс в npm** — патч (0.19.3+) доступен только через их собственный CDN. Это прямо касается нас: мы парсим файлы, загруженные пользователями, — ровно тот сценарий, который эксплуатирует уязвимость.
  - В `package.json` зависимость `xlsx` уже указывает на патченную версию с CDN SheetJS (`https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz`), а не на npm-реестр.
  - Это единственный официально рекомендованный способ получить пропатченную версию — не баг конфигурации, а состояние проекта SheetJS на данный момент.
  - После `npm install` стоит прогнать `npm audit` ещё раз и убедиться, что xlsx больше не числится уязвимым.
